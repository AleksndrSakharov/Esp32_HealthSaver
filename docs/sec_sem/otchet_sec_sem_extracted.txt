ВВЕДЕНИЕ

В предыдущем семестре была разработана базовая аппаратно-программная часть системы мониторинга здоровья: BLE-датчик давления на базе ESP32, центральный хаб для приема измерений и сохранение данных на SD-карту. Такая архитектура позволила подтвердить работоспособность выбранного подхода, однако для практического применения системы требовалось расширить ее возможностями сетевой передачи, централизованного хранения и удобного просмотра результатов.
В рамках данного семестра работа была направлена на развитие системы в сторону полноценной IoT-инфраструктуры. Основной задачей стало создание серверной части, которая принимает измерения от ESP32-хаба, сохраняет их в базе данных и предоставляет веб-интерфейс для просмотра истории измерений, таблиц и графиков. Дополнительно была реализована автоматическая настройка WiFi на хабе, чтобы устройство можно было использовать без ручного изменения файла конфигурации.
Отдельное внимание было уделено устойчивости передачи данных. В реальных условиях WiFi-сеть или сервер могут быть временно недоступны, поэтому хаб должен сохранять полученные BLE-измерения на SD-карту и отправлять их позже. Также была исследована совместная работа BLE и WiFi на ESP32, так как оба интерфейса используют общий радиомодуль и оказывают влияние на доступную память устройства.

1. ЦЕЛИ И ЗАДАЧИ ПРАКТИКИ
Цель практики: развитие системы мониторинга здоровья на базе ESP32 путем добавления серверной части, веб-интерфейса, автоматической настройки WiFi и надежной передачи измерений от BLE-датчика через центральный хаб.
Задачи практики:
1. проанализировать существующую реализацию BLE-датчика и центрального ESP32-хаба;
2. разработать серверную часть на ASP.NET Core для приема и хранения измерений;
3. реализовать API для передачи данных с хаба на сервер;
4. настроить автоматическое обнаружение сервера в локальной сети через UDP broadcast;
5. исключить ручное указание адреса сервера в конфигурации хаба;
6. реализовать WiFi provisioning на ESP32 с вводом SSID и пароля через встроенный веб-сервер;
7. добавить сохранение WiFi-настроек во внутреннюю память ESP32 и сброс конфигурации через кнопку BOOT;
8. исследовать и доработать совместную работу BLE и WiFi на ESP32;
9. реализовать сохранение измерений на SD-карту и очередь последующей отправки;
10. разработать веб-интерфейс для просмотра истории измерений, таблиц и графиков;
11. настроить WebSocket-обновления для отображения новых измерений без ручного обновления страницы;
12. провести тестирование полного цикла передачи данных от BLE-датчика до отображения результатов на сайте.
2. ТЕОРЕТИЧЕСКАЯ ЧАСТЬ
2.1. Серверная часть IoT-системы мониторинга здоровья
В системах интернета вещей серверная часть выполняет роль центрального узла, который принимает данные от устройств, сохраняет их, обрабатывает и предоставляет пользователю удобный доступ к результатам. В рамках разрабатываемой системы сервер необходим для того, чтобы ESP32-хаб не был конечной точкой хранения данных, а мог передавать измерения в централизованное приложение. Это позволяет просматривать историю измерений с любого устройства в локальной сети, строить графики, анализировать динамику показателей и в дальнейшем расширять систему новыми датчиками.
Для реализации серверной части была выбрана платформа ASP.NET Core. Она позволяет разрабатывать веб-приложения, REST API и WebSocket-сервисы в рамках одного проекта. ASP.NET Core хорошо подходит для локального сервера медицинской IoT-системы, так как поддерживает маршрутизацию HTTP-запросов, работу со статическими файлами веб-интерфейса, подключение базы данных и фоновую отправку служебных сообщений, например UDP broadcast для обнаружения сервера.
В разработанной системе сервер выполняет несколько основных функций. Во-первых, он принимает измерения давления от ESP32-хаба. Во-вторых, сохраняет метаданные измерений в базе данных PostgreSQL. К таким метаданным относятся идентификатор измерения, устройство, тип датчика, единица измерения, частота дискретизации, количество полученных значений, время начала и завершения измерения. В-третьих, сервер хранит сами массивы измерений в бинарных файлах формата float32 little-endian. Такой подход уменьшает нагрузку на базу данных и позволяет эффективно работать с большими массивами числовых данных.
2.2. REST API и передача измерений
Для обмена данными между ESP32-хабом и сервером используется REST API. REST API представляет собой набор HTTP-маршрутов, через которые клиентское устройство может отправлять или получать данные. В данной системе клиентом является ESP32-хаб, а сервер принимает запросы и сохраняет измерения. Использование HTTP удобно тем, что этот протокол широко поддерживается, хорошо отлаживается и может быть протестирован не только с ESP32, но и с компьютера.
Изначально передача измерений была разделена на несколько этапов: создание измерения, отправка частей массива и завершение передачи. Такая схема удобна для больших данных, так как позволяет разбивать массив значений на несколько небольших фрагментов. Однако при работе с ESP32 важно учитывать ограничения оперативной памяти и сетевых ресурсов. Каждый HTTP-запрос создает дополнительную нагрузку, поэтому в проекте был также реализован упрощенный endpoint, позволяющий отправить измерение одним запросом.
В итоговом варианте хаб может отправлять на сервер JSON-объект, содержащий идентификатор устройства, тип датчика, единицу измерения, частоту дискретизации и массив значений давления. Сервер принимает этот объект, проверяет корректность данных, сохраняет массив измерений и создает запись в базе данных. После успешной обработки сервер возвращает идентификатор измерения, по которому оно может быть найдено в истории.
2.3. WebSocket для обновления интерфейса в реальном времени
Обычный REST API хорошо подходит для получения данных по запросу, но он не решает задачу мгновенного обновления интерфейса. Если использовать только HTTP-запросы, веб-странице пришлось бы постоянно опрашивать сервер, чтобы узнать, появились ли новые измерения. Такой подход называется polling и приводит к лишней нагрузке на сервер и сеть.
Для решения этой задачи в проекте используется WebSocket. WebSocket — это протокол постоянного двустороннего соединения между браузером и сервером. После открытия соединения сервер может сам отправлять сообщения клиенту без ожидания нового HTTP-запроса. Это особенно удобно для систем мониторинга, где новые данные должны появляться на экране сразу после получения.
В разработанном веб-интерфейсе WebSocket используется для уведомления браузера о новых измерениях. Когда сервер получает и сохраняет данные от ESP32-хаба, он отправляет событие в подключенные клиенты. После этого веб-интерфейс автоматически добавляет новую запись в список измерений и может открыть соответствующую таблицу или график. Благодаря этому пользователю не нужно вручную обновлять страницу.
2.4. UDP broadcast для автоматического обнаружения сервера
Одной из проблем IoT-систем является настройка адреса сервера. Если вручную прописывать IP-адрес сервера в прошивке ESP32, то при изменении сети или адреса компьютера устройство перестанет отправлять данные. Для устранения этой проблемы в системе используется механизм автоматического обнаружения сервера через UDP broadcast.
UDP — это сетевой протокол, который позволяет отправлять короткие сообщения без установки постоянного соединения. В отличие от TCP, UDP не гарантирует доставку каждого пакета, но работает проще и быстрее. Для задачи обнаружения сервера это подходит, потому что сообщение можно отправлять периодически, и потеря одного пакета не является критичной.
Broadcast означает отправку сообщения всем устройствам в локальной сети. Сервер периодически отправляет UDP-сообщение, содержащее свой HTTP-адрес, например http://192.168.1.93:5000. ESP32-хаб после подключения к WiFi слушает заданный UDP-порт и получает это сообщение. После этого хаб сохраняет найденный адрес и использует его для отправки HTTP-запросов. Таким образом, адрес сервера больше не нужно указывать вручную в файле конфигурации.
2.5. WiFi provisioning на ESP32

WiFi provisioning — это процесс первичной настройки подключения устройства к беспроводной сети. В ранней версии проекта SSID и пароль WiFi задавались в файле secrets.h, что требовало перекомпиляции прошивки при изменении сети. Для устройства, которое должно использоваться как самостоятельный хаб, такой способ неудобен.
В реализованной системе при отсутствии сохраненных WiFi-настроек ESP32-хаб запускает собственную точку доступа. Пользователь подключается к этой сети с телефона или компьютера и открывает локальную страницу настройки. На странице отображается форма с двумя полями: SSID и пароль основной WiFi-сети. После отправки формы хаб сохраняет данные во внутреннюю энергонезависимую память ESP32.
Для хранения настроек используется NVS-память через библиотеку Preferences. Это позволяет сохранять параметры между перезагрузками устройства. После успешного сохранения ESP32 перезапускается, подключается к указанной сети и начинает поиск сервера через UDP broadcast. Также реализована возможность сброса конфигурации через кнопку BOOT, чтобы пользователь мог заново настроить сеть без перепрошивки устройства.

2.6. Совместная работа BLE и WiFi на ESP32

ESP32 поддерживает как WiFi, так и Bluetooth Low Energy, однако оба интерфейса используют общий радиомодуль. Поэтому их одновременная работа требует учета ограничений микроконтроллера. При активной BLE-передаче и одновременной отправке HTTP-запросов по WiFi могут возникать задержки, нехватка памяти и ошибки сетевой передачи.
BLE используется для приема данных от датчика давления. Датчик передает измерения в виде последовательности сообщений: начало измерения, набор значений и завершение измерения. WiFi используется для передачи уже полученных данных на сервер. Основная сложность заключается в том, что хаб должен не потерять BLE-данные и при этом корректно отправить измерения по сети.
Для повышения надежности была реализована очередь измерений на SD-карте. После получения измерения хаб сначала сохраняет его в файл, а уже затем пытается отправить на сервер. Если WiFi или сервер недоступны, файл остается на SD-карте и отправляется позже. Такой подход снижает риск потери данных и позволяет разделить прием BLE-измерений и сетевую отправку.
Дополнительно была применена библиотека NimBLE-Arduino. Она является более легкой альтернативой стандартной ESP32 BLE Arduino и позволяет уменьшить расход памяти при работе BLE. Это важно для проекта, так как свободная оперативная память напрямую влияет на стабильность HTTP-запросов и возможность одновременной работы BLE и WiFi.


3. ПРАКТИЧЕСКАЯ ЧАСТЬ
3.1. Общая архитектура системы
Итоговая система состоит из трех основных частей: BLE-датчика давления, центрального ESP32-хаба и серверной части HealthSaver.Server. Датчик передает измерения по BLE. Хаб принимает данные, сохраняет их на SD-карту и отправляет на сервер по WiFi. Сервер сохраняет измерения и предоставляет веб-интерфейс для анализа результатов.
Обмен данными между датчиком и хабом основан на текстовом протоколе HS1. Передача начинается сообщением старта, далее идут строки с измеренными значениями, после чего отправляется сообщение окончания с количеством сэмплов. Хаб разбирает эти сообщения и формирует запись измерения.
H1S;p;mmHg;1;1
H1D;0;120.55
H1D;1;118.30
H1E;2
После получения полного измерения данные записываются в файл очереди на SD-карте. В оперативной памяти хаб хранит только путь к файлу, что снижает нагрузку на память и позволяет переживать временную недоступность сети или сервера.
3.2. Реализация серверной части
Серверная часть реализована в проекте HealthSaver.Server на ASP.NET Core. В сервере настроены контроллеры, статическая выдача веб-интерфейса, WebSocket endpoint, подключение к PostgreSQL через Entity Framework Core и сервис хранения бинарных массивов измерений.
Метаданные измерений хранятся в базе данных: устройство, тип датчика, единица измерения, частота дискретизации, количество сэмплов, статус измерения и контрольная сумма. Сами массивы значений сохраняются в каталог Data/raw в формате float32 little-endian. Такой подход уменьшает нагрузку на базу данных и позволяет эффективно читать серии для построения графиков.
Для приема данных были реализованы endpoint'ы /api/ingest/start, /api/ingest/chunk, /api/ingest/complete, а также упрощенный endpoint /api/ingest/measurement для отправки измерения одним запросом. Последний вариант оказался полезен для ESP32, так как уменьшает количество HTTP-соединений и снижает риск ошибок при передаче.
Для получения данных веб-интерфейс использует /api/measurements, /api/measurements/{id} и /api/measurements/{id}/series. Сервер также отправляет события measurementStarted, liveChunk и measurementCompleted через WebSocket, чтобы интерфейс мог обновляться без ручной перезагрузки.

3.3. Реализация WiFi provisioning на хабе
В прошивке хаба был реализован механизм первичной настройки WiFi. Если в памяти ESP32 отсутствуют сохраненные параметры сети, устройство запускает точку доступа ESP32HUB и веб-сервер на адресе 192.168.4.1. На странице настройки пользователь вводит SSID и пароль основной сети.
Для хранения параметров используется библиотека Preferences, которая работает с NVS-памятью ESP32. После сохранения данных хаб перезапускается, подключается к указанной сети и начинает слушать UDP broadcast от серверной части. Это позволило убрать необходимость вручную задавать SERVER_BASE_URL в secrets.h.
Дополнительно реализован сброс настроек через кнопку BOOT. При удержании кнопки во время стартового окна хаб удаляет сохраненную конфигурацию и переходит в режим provisioning. Такая схема удобна для демонстрации проекта и для переноса устройства между разными WiFi-сетями.
Алгоритм первичной настройки хаба включает следующие шаги:
• проверка наличия сохраненных WiFi-настроек в NVS-памяти ESP32;
• запуск точки доступа ESP32HUB при отсутствии конфигурации;
• отображение HTML-формы для ввода SSID и пароля;
• сохранение введенных параметров и перезапуск устройства;
• подключение к основной WiFi-сети и ожидание UDP-сообщения от сервера.
3.4. Очередь измерений и хранение на SD-карте
Для повышения надежности передачи была реализована SD-backed очередь измерений. После завершения BLE-передачи хаб записывает измерение в каталог /queue на SD-карте. Файл содержит метаданные и набор числовых значений. В очередь FreeRTOS помещается только ссылка на файл.
Если WiFi или сервер недоступны, файл остается на SD-карте и будет отправлен позже. При запуске устройства хаб сканирует каталог очереди и добавляет найденные файлы в очередь отправки. Это защищает данные от потери при перезагрузке или нестабильной сети.
В сетевой задаче выполняется проверка доступности WiFi, наличие найденного адреса сервера, объем свободной памяти и состояние BLE-передачи. При успешной отправке сервер возвращает идентификатор измерения, после чего файл удаляется с SD-карты. При ошибке отправки файл сохраняется для повторной попытки.
Для уменьшения расхода оперативной памяти измерение не хранится в очереди как массив float. Вместо этого используется структура со строковым путем к файлу. Такой подход особенно важен при одновременной работе BLE и WiFi, когда доступная память ESP32 заметно уменьшается.
BLE measurement complete
-> write /queue/m_<time>_<count>.txt
-> enqueue file path
-> wait for WiFi and server
-> POST /api/ingest/measurement
-> delete file after success
3.5. Веб-интерфейс и WebSocket-обновления
Веб-интерфейс размещен в каталоге wwwroot серверного проекта и открывается через браузер. Интерфейс содержит список измерений, фильтры по устройству и типу датчика, область подробной информации и график значений. При выборе записи пользователь видит метаданные и временной ряд измерения давления.
Для графиков реализовано отображение подсказки при наведении на точку: показывается значение, время и единица измерения. Список измерений адаптирован под прокрутку, а новая запись появляется в интерфейсе после получения WebSocket-события от сервера.
Таким образом, пользователь может наблюдать результаты без ручного обновления страницы. Это важно для системы мониторинга здоровья, где новые измерения должны появляться сразу после завершения передачи с устройства.
3.6. Тестирование и отладка системы
Тестирование выполнялось поэтапно. Сначала проверялось подключение хаба к WiFi и обнаружение сервера через UDP broadcast. Затем проверялась передача измерения от BLE-датчика, запись на SD-карту и отправка данных на сервер. После этого проверялось появление новой записи в веб-интерфейсе и обновление графика.
В ходе тестирования были выявлены ситуации, когда хаб успешно принимал данные по BLE, но не мог отправить их на сервер из-за временной недоступности WiFi, сервера или нехватки памяти. Для таких случаев была добавлена отложенная отправка. Логи устройства стали показывать не только факт ошибки, но и причину: отсутствие WiFi, отсутствие server URL, недостаток heap или неудачную HTTP-запись.
Отдельно проверялся режим восстановления после перезагрузки. Если на SD-карте оставались неотправленные файлы, хаб при следующем запуске заново добавлял их в очередь и отправлял после подключения к серверу. Это подтвердило, что данные не теряются при сбоях питания или перезапуске устройства.
Для снижения нагрузки на ESP32 была выполнена миграция BLE-клиента на NimBLE-Arduino. После этого размер прошивки и потребление памяти уменьшились, что улучшило условия для параллельной работы BLE и WiFi.

4. РЕЗУЛЬТАТЫ РАБОТЫ
В ходе практики были получены следующие результаты:
•  разработана серверная часть HealthSaver.Server на ASP.NET Core;
•  реализовано API для приема измерений давления от ESP32-хаба;
• настроено хранение метаданных в PostgreSQL и сырых массивов измерений в формате .f32;
• реализован механизм UDP broadcast для автоматического обнаружения сервера хабом;
• добавлен WiFi provisioning на ESP32 с точкой доступа, веб-формой и сохранением настроек в NVS;
• добавлен сброс WiFi-конфигурации через кнопку BOOT;
• реализована очередь измерений на SD-карте с повторной отправкой при доступности сети;
• исследована совместная работа BLE и WiFi на ESP32, выполнена оптимизация с использованием NimBLE-Arduino;
• разработан веб-интерфейс с историей измерений, таблицами, графиками и WebSocket-обновлениями;
• проверен полный цикл передачи данных от BLE-датчика до отображения результатов на сайте.
Практическое тестирование показало, что система способна принимать измерения от BLE-датчика, сохранять их на хабе, подключаться к WiFi, автоматически находить сервер и передавать данные в веб-приложение. При временной недоступности сервера измерения не теряются, а остаются в очереди на SD-карте.
В процессе разработки также были выявлены ограничения ESP32 при одновременной работе BLE и WiFi. Основными проблемами стали нехватка памяти и ошибки сетевой записи при высокой нагрузке. Для уменьшения этих проблем была применена более легкая BLE-библиотека NimBLE-Arduino и введена логика отложенной отправки данных.
ЗАКЛЮЧЕНИЕ
В результате выполнения практики система мониторинга здоровья была расширена от автономного BLE-прототипа до более полноценной IoT-системы с серверной частью и веб-интерфейсом. Центральный хаб получил возможность настраиваться без перепрошивки, автоматически находить сервер в локальной сети и передавать измерения по WiFi.
Реализованная SD-backed очередь повысила надежность системы, поскольку измерения сохраняются локально и не теряются при временных проблемах с сетью. Серверная часть обеспечивает прием, хранение и отображение данных, а WebSocket-обновления делают интерфейс удобным для наблюдения за новыми измерениями.
Дальнейшее развитие проекта может быть связано с повышением устойчивости параллельной работы BLE и WiFi, расширением набора поддерживаемых датчиков, улучшением анализа графиков давления и добавлением пользовательских сценариев для долговременного мониторинга состояния здоровья.
